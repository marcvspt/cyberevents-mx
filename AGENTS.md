# Instrucciones para agentes

Estas instrucciones se aplican a todo el repositorio.

## Contribuciones y mensajes de commit

- Seguir [CONTRIBUTING.md](CONTRIBUTING.md) para preparar contribuciones y redactar mensajes de commit; esa guía define el formato, los prefijos y la separación de cambios independientes.
- Al entregar cambios, incluir siempre una recomendación de mensaje de commit para los cambios de la tarea. Si se solicita cubrir todos los cambios pendientes, revisar `git status`, los diffs preparados y sin preparar y los archivos nuevos no ignorados antes de redactarla.
- Recomendar un mensaje no autoriza realizar el commit ni publicar cambios.

## Ejecución de comandos y dependencias

- Las consultas SQL para actualizar la base de datos de producción deben entregarse directamente aquí en el chat, en bloques de código SQL listos para copiar. No generes archivos `.sql` ni otros archivos para entregar esas consultas.
- El propietario ejecuta todos los comandos de `pnpm`. No ejecutes `pnpm install`, `pnpm add`, `pnpm update`, `pnpm remove`, `pnpm run`, `pnpm build`, `pnpm exec`, `pnpm dlx` ni otros comandos de pnpm.
- Cuando hagan falta desarrollo, build, preview, comprobaciones o cambios de dependencias, indica el comando exacto, para qué sirve y desde qué directorio debe ejecutarse. Espera los resultados del propietario si necesitas esa validación para continuar.
- No eludas esta regla usando npm, yarn, bun, npx, ejecutables directos o scripts equivalentes para realizar las tareas reservadas al propietario. No instales ni actualices herramientas o dependencias por tu cuenta.
- Puedes explorar archivos, editar código y documentación, y realizar comprobaciones de solo lectura como `git diff --check`.
- Al entregar cambios, distingue las comprobaciones realizadas de las pendientes. No afirmes que el build o las pruebas pasaron si no se ejecutaron; indica los comandos que debe ejecutar el propietario.

## Contexto del proyecto

- Sitio sobre eventos de ciberseguridad en México en español, construido con Astro 7, TypeScript, Tailwind CSS 4 y `@tailwindcss/typography`. Consulta `package.json` para las versiones concretas y mantén los cambios compatibles con ellas.
- El destino de despliegue configurado es Netlify, con `@astrojs/netlify` y salida de servidor (`output: 'server'`) en `astro.config.mjs`. Mantén la compatibilidad con ese entorno; no cambies el adaptador, el proveedor ni el modo de salida salvo que el alcance solicitado lo requiera.
- Sigue las convenciones de Astro: componentes `.astro`, rutas basadas en archivos y colecciones de contenido. Conserva el funcionamiento de los eventos durante la navegación con `ClientRouter` y limpia los listeners cuando se reemplaza la página.
- Prioriza el SSR de Astro cuando sea viable y aporte valor, por ejemplo para datos actualizados por petición, autenticación o contenido personalizado. Favorece resolver los datos y generar el HTML en Astro, manteniendo en el cliente la lógica que necesite interacción con el navegador.
- Inicio, Eventos, Archivo y fichas usan SSR por petición para actualizar los estados temporales. Acerca de, RSS, robots y el sitemap de fichas declaran `prerender = true`. Conserva esta distinción y documenta cualquier cambio. Los Markdown cargados por `glob` siguen incorporándose durante el build; añadir o editar contenido requiere despliegue.
- Usa Tailwind CSS 4 para los estilos y su configuración existente mediante `@tailwindcss/vite`, `@import`, `@theme` y `@plugin`. Los estilos base de esquema oscuro, fondo, tipografía, selección y scroll se expresan con utilidades en `BaseLayout.astro`. Para el contenido Markdown, conserva `@tailwindcss/typography`, las clases `prose` / `prose-invert` y los modificadores `prose-*` en la plantilla; no dupliques variables internas `--tw-prose-*` en CSS global. Conserva en CSS el gradiente radial, los patrones compartidos con `@apply`, el foco y la reducción global de movimiento; evita duplicar utilidades disponibles o introducir configuraciones de otras versiones de Tailwind.
- `src/pages/` define las rutas; `src/components/` contiene componentes reutilizables y `src/layouts/` las plantillas.
- La colección `events` se define en `src/content.config.ts` y carga artículos desde `src/data/events/`. Respeta el esquema del frontmatter y el filtro de borradores `draft`.
- Las imágenes públicas se guardan en `public/`; los estilos globales, en `src/styles/global.css`.
- Debes usar los alias definidos en `tsconfig.json` para los imports internos de `src/`: `@/pages/`, `@/layouts/`, `@/components/`, `@/lib/` y `@/styles/`. No hay un alias `@/scripts/` ni un alias genérico para cualquier ruta. Usa la extensión real explícita e importa el archivo concreto, sin barrels ni reexportaciones de conveniencia. En archivos que ejecuta Node fuera de Astro, como `astro.config.mjs`, usa rutas relativas compatibles con ese entorno. Respeta el estilo de los archivos que modifiques.

## Coherencia de la UI

- La interfaz tiene únicamente tema oscuro. Los colores semánticos se definen mediante `@theme` en `src/styles/global.css`: `background`, `surface`, `surface-raised`, `border`, `foreground`, `muted`, `primary`, `secondary` y `danger`. Usa esas utilidades de Tailwind; no agregues colores por nombre de tonalidad ni valores hexadecimales en componentes. `primary` es el acento azul y `secondary` el turquesa.
- Reutiliza `page-shell`, `text-link`, `button-primary`, `button-secondary` y `status-badge` para conservar el patrón visual. Las tarjetas compartidas se implementan en `EventCard.astro`; cabecera y pie se comparten desde `BaseLayout.astro`. Respeta foco visible, enlace para saltar al contenido y reducción de movimiento.
- Usa SVG para los iconos de la interfaz, sin emojis ni caracteres Unicode como sustitutos. Reutiliza `ArrowIcon.astro` para flechas de enlaces y acciones; conserva los iconos decorativos ocultos a lectores de pantalla.
- No agregues eyebrows decorativos. Cada ficha comienza con un breadcrumb Inicio / Eventos o Archivo / título, seguido del estado y las categorías antes del título. El texto de lectura es blanco puro (`foreground` y `muted`); usa tamaños y pesos para su jerarquía, conservando acentos en enlaces y etiquetas.
- Los textos propios fuera de Markdown están centralizados en `TEXTS_GENERAL` de `src/lib/texts.ts`: interfaz, metadatos de páginas (`pages`), marca (`site`), etiquetas de recursos externos (`externalResources`), mensajes de validación (`validation`) y errores de configuración (`errors`). Edita ese objeto en vez de incluir nuevas frases en plantillas o módulos. `SITE_LOCALE` de `src/lib/site.ts` configura el idioma del HTML, RSS, fechas, ordenación alfabética y zona horaria; el formato técnico de `getToday` conserva su locale fijo y usa `SITE_LOCALE.timeZone` (`America/Mexico_City`). No hay selección de idioma ni rutas localizadas. El contenido editorial de eventos permanece en Markdown.
- `SITE_PAGES` y `MAIN_NAVIGATION` viven en `src/lib/navigation.ts`; los enlaces usan `id`, `label` y `href`, y los metadatos usan `title` y `description`. Tipos de sitio en `src/lib/types/site.ts`; tipos de eventos derivados de la colección en `src/lib/types/event.ts`. Importar `SITE_DATA` directamente desde `src/lib/site.ts`.
- La sección `/events/` se denomina «Eventos», no «Agenda», en navegación, breadcrumbs y acciones. «Agenda» puede seguir apareciendo en contenido editorial y URL oficiales; no cambies esos enlaces. El footer tiene marca y descripción a la izquierda, aviso sobre fuentes públicas en la columna central en escritorio y Recursos Externos a la derecha, y una franja inferior centrada. Sus enlaces se definen en `EXTERNAL_RESOURCES` de `src/lib/links.ts`, con `target="_blank"` y `rel="noopener noreferrer"`. El aviso de licencia vive en `TEXTS_GENERAL.footer` y su enlace en `LICENSE_LINK` del mismo módulo. No muestra un enlace RSS, pero conserva `/rss.xml`.
- La marca visible es «CyberEvents», sin «.MX»; su nombre sigue centralizado en `TEXTS_GENERAL.site`. `SITE_DATA.logo` usa `/img/logo.svg`, un SVG horizontal de 188 × 36 px con escudo y nombre convertido a trazados. `public/img/icon.svg` contiene el icono independiente, sin texto y con `viewBox` cuadrado; `BaseLayout.astro` lo declara como favicon con `rel="icon"`, `type="image/svg+xml"` y `sizes="any"`. La URL `/img/icon.svg` sustituye a la declaración anterior de `/favicon.svg` para cambiar la clave de caché del navegador. `public/favicon.svg` conserva una copia idéntica para la ruta previa y `public/favicon.ico` contiene el mismo escudo en un ICO real de 16, 32 y 48 px para solicitudes automáticas. Mantén los iconos y el símbolo del logo sincronizados en geometría y colores; no guardes PNG renombrados como `.ico`. Los colores fijos de estos recursos SVG corresponden a los tokens del tema oscuro de `global.css`. La cabecera muestra el logo a 36 px de alto y hasta 200 px de ancho, conservando proporción y texto alternativo; actualiza sus atributos de dimensiones si se sustituye el recurso. Si `logo` está vacío, se muestra el escudo con el nombre como texto. Los cambios de recursos y de la declaración del favicon requieren build y despliegue para actualizar el sitio publicado. Este cambio de marca no modifica el dominio ni los identificadores del repositorio.
- `Header.astro` muestra los enlaces en línea desde `md`; en anchos menores usa un menú de hamburguesa con `details` y `summary`, accesible también sin JavaScript y con scroll interno en pantallas bajas. `SupportMenu.astro` añade «Apóyame» como desplegable en escritorio y panel expandible en el flujo del menú móvil, con enlaces de ancho completo y altura mínima de 56 px en móvil; usa `SUPPORT_LINKS` de `src/lib/links.ts` y `TEXTS_GENERAL.support`, con enlaces externos en pestaña nueva y `rel="noopener noreferrer"`. Ambos menús usan `data-navigation-menu` y se cierran al elegir un enlace, hacer clic fuera o antes de reemplazar la página con `ClientRouter`; cerrar el menú principal también restablece los paneles internos mediante la función de cierre compartida y un listener de `toggle` en captura. Escape cierra el menú abierto más interno que contiene el foco y devuelve el foco a su `summary`. Los listeners se registran una sola vez y consultan el DOM actual. El footer apila y centra todos sus bloques por debajo de `lg`; desde `lg` mantiene tres columnas alineadas a la izquierda.

- Mantén una UI coherente entre todas las secciones de la aplicación: inicio, catálogo, eventos y cualquier sección nueva. Respeta la paleta, tipografía, jerarquía de títulos, espaciados, anchos de contenido, bordes, iconografía y animaciones existentes.
- Reutiliza los layouts, componentes y estilos compartidos para elementos equivalentes, como navegación, tarjetas, botones, enlaces y etiquetas. Si necesitas una variante, intégrala en el patrón existente y evita crear estilos aislados que rompan la coherencia visual.
- Mantén consistentes los estados de interacción (hover, foco, activo, deshabilitado), los mensajes y el comportamiento en móvil y escritorio. Conserva la accesibilidad y la navegación por teclado al modificar la UI.
- Al cambiar un componente compartido, considera su efecto en todas las secciones que lo usan y señala al propietario qué vistas debe comprobar visualmente.
- En `EventSummaryLayout.astro`, el bloque de título y descripción está fuera y encima de la cuadrícula. El aside empieza junto a la imagen, debajo de la cabecera de la ficha: usa `lg:sticky lg:top-8` y limita su altura con scroll interno para mantener accesibles los enlaces en pantallas bajas. En móvil sigue el flujo normal. Los enlaces externos de las fichas usan `target="_blank"` y `rel="noopener noreferrer"`; los internos conservan su navegación. El script de la plantilla aplica la misma regla a enlaces externos del cuerpo Markdown al cargar y en `astro:page-load`. El listener global se registra una vez por el script procesado de Astro y no conserva referencias a páginas reemplazadas.

## Events, RSS y sitemap

- `DATA.md` es la referencia de intención del producto: directorio y archivo histórico de ciberseguridad en México. Su investigación es contexto, no evidencia de fechas verificadas; confirma los datos reales con fuentes oficiales antes de publicarlos.
- Las rutas actuales son `/events/`, `/events/archive/` y `/events/[id]/`; conserva estas URL hasta que se solicite una migración. El ID procede del archivo Markdown cargado por `glob`, sin un campo `slug` adicional. Reserva el ID `archive` y su prefijo `archive/` para las páginas del archivo; no los uses para fichas.
- Los archivos de fichas usan el año al inicio: `YYYY-nombre.md`. Si hay varias ediciones del mismo evento en un año, usa `YYYY-MM-nombre.md` y añade el día (`YYYY-MM-DD-nombre.md`) solo si hace falta. Para ciudades o fases distintas, usa sufijos descriptivos. Sin año confirmado, no lo inventes: conserva el nombre sin prefijo hasta verificarlo. Los borradores de ediciones tentativas mantienen su condición de borrador, aunque su nombre tenga año.
- Las imágenes específicas de una edición comparten el nombre base de la ficha y conservan su formato real. Las marcas e ilustraciones reutilizables viven en `public/img/events/shared/`. Actualiza el campo `image` cuando se trasladan imágenes.
- Las fichas nuevas se crean siempre sin `image` ni `imageAlt` para usar la ilustración predeterminada de `EventVisual.astro`. Entrega al propietario los enlaces oficiales de descarga de las imágenes que encuentres, identificados por evento; no descargues ni incorpores esas imágenes salvo petición expresa. Si no encuentras una imagen oficial, indícalo sin inventar enlaces. Conserva las imágenes de las fichas existentes salvo que se solicite cambiarlas.
- Las fichas usan IDs con el año al inicio. No se conservan redirecciones de los nombres anteriores. Al renombrar otra ficha, actualiza sus referencias internas. Mantén RSS, canónicas y sitemap apuntando a los IDs actuales.
- La sección Eventos (`/events/`) separa «En curso y muy pronto» (en curso o con inicio en los próximos 30 días, límite inclusivo), «Próximos» (inicio posterior), «Fechas por anunciar» y «Cancelados». `isEventNear` y `NEAR_EVENT_DAYS` de `src/lib/events/status.ts` definen la cercanía con días de calendario a partir de `America/Mexico_City`. Los finalizados también aparecen en «Descubre cómo fue» si terminaron hace menos de dos meses de calendario (`RECENT_EVENT_MONTHS` e `isEventRecent`): se usa `endDate` o `startDate`, se resta el plazo al día actual y se excluye la fecha límite exacta. Si el día no existe en el mes de corte, se ajusta a su último día. Todos los finalizados siguen disponibles en el archivo.
- `src/pages/events/archive/index.astro` consume `getArchivedEventGroups` para mostrar solo eventos publicados finalizados. Agrupa por el año de `startDate`, incluso si el evento cruza de año, y ordena años y fechas de inicio de más reciente a más antiguo. El archivo reutiliza `EventCard.astro`, tiene navegación por anclas de año y se renderiza por petición y se incluye en el sitemap como página de ruta fija.
- Cada ficha necesita `title`, `description`, `updatedAt`, `format` y `categories`. Las fechas son cadenas de calendario `YYYY-MM-DD`, entre comillas en YAML. `startDate` es opcional: su ausencia significa «Próximamente». Omite los datos desconocidos; no uses fechas ficticias ni `null`.
- La redacción pública de las fichas se centra en información confirmada y útil sobre el evento. Omite los datos desconocidos sin enumerarlos ni explicar su ausencia, las decisiones sobre el frontmatter o los límites de la investigación. Usa frases afirmativas para describir el alcance y los requisitos. Las notas de verificación y los pendientes editoriales corresponden a la documentación de investigación o a borradores excluidos de publicación.
- Las categorías admitidas por el esquema son `conference`, `congress`, `meetup`, `ctf`, `hackathon`, `bsides`, `workshop`, `summit`, `forum`, `academic` y `community`. `hackathon` se muestra como «Hackatón» mediante `TEXTS_GENERAL.event.categories`; los tipos siguen derivándose de la colección. Distingue competencias CTF de hackatones de creación o investigación y explica en el Markdown su elegibilidad y alcance temático. Convierte las fechas y horas publicadas en UTC al calendario de `America/Mexico_City` antes de guardar `startDate` y `endDate`; no uses el cierre de inscripción como fecha de competencia. Separa clasificatoria y final cuando sus fechas o modalidades sean distintas.
- `src/lib/events/status.ts` calcula «Próximamente», «Próximo», «En curso», «Finalizado» y «Cancelado». `cancelled` y `registrationOpen` son datos manuales independientes; no guardes un estado temporal general en frontmatter. Sin `endDate`, el evento dura un día. Los límites diarios usan `America/Mexico_City`.
- Los estados y el CFP se calculan por petición con el día de `America/Mexico_City`. `src/middleware.ts` envía `Cache-Control: private, no-store` para inicio y las rutas de eventos. No hay función programada ni build hook necesarios para el cambio temporal de secciones. Una página ya abierta se actualiza al recargar o navegar; el contenido editorial nuevo sigue requiriendo build y despliegue.
- El CFP admite URL, fechas opcionales y estado editorial opcional. Un cierre explícito prevalece; después de `closes` está cerrado, antes de `opens` está anunciado y desde `opens` está abierto hasta el cierre. Sin fecha de apertura se usa el estado editorial o «por anunciar». Las fechas límite son inclusivas.
- Se admiten ubicación, organizador, precio, temas, redes, hashtags sin `#`, recursos (fotos, videos, slides y aftermovie) y verificación. `verification.status: verified` exige `checkedAt` y al menos una URL en `sources`; usa fuentes oficiales y no marques información como verificada por haberla encontrado en `DATA.md`.
- Todas las fichas tienen en su aside el CTA «Busca el evento en redes» (`#conversation`), con búsquedas en X, Instagram, YouTube y LinkedIn. Usa los hashtags cuando están disponibles y, en su ausencia, el título del evento; no inventes etiquetas oficiales. Instagram usa su página de hashtag o la búsqueda por palabra clave según corresponda. Las tarjetas solo llevan a la ficha y no incluyen un enlace adicional a la conversación. Los textos del CTA se editan en `TEXTS_GENERAL.event`. El archivo contiene una selección verificada de ediciones de 2024 y 2025 y admite más fichas bajo el mismo esquema.
- El ejemplo de publicación en `README.md` es ficticio y debe conservar `draft: true` si se copia a una ficha. Los borradores validan el esquema, pero se excluyen de inicio, catálogo, rutas de fichas y RSS. Las fichas SSR resuelven el ID mediante `getPublishedEvents`; IDs desconocidos y borradores devuelven 404. El sitemap de fichas usa el mismo filtro.
- `updatedAt` es la fecha obligatoria de última actualización editorial de la ficha; alimenta la fecha y el orden del RSS y se muestra en la ficha. Conserva este nombre exacto y no lo confundas con `startDate`. `featured` está reservado y todavía no determina la selección. `image` es una ruta local desde `public/`, con `imageAlt` opcional; `EventVisual.astro` muestra la imagen en tarjetas y fichas o una ilustración SVG si falta. Las imágenes oficiales están en `public/img/events/`; no uses carteles de otra edición como si fueran del año de la ficha.

- El dominio se define una sola vez en la propiedad `site` de `astro.config.mjs`. Las páginas usan `Astro.site` y las rutas usan `context.site` (o su propiedad desestructurada `site`) para generar URL absolutas. `SITE_DATA` en `src/lib/site.ts` obtiene nombre y descripción de `TEXTS_GENERAL.site` y configura la ruta del logo; no agregues un dominio ni un fallback de URL allí. Canónicas, RSS y robots requieren que `site` esté configurado.
- El sitemap usa `@astrojs/sitemap` con `customSitemaps: [new URL('/sitemap-events.xml', site).href]` para registrar el sitemap de fichas en el índice. `src/pages/robots.txt.ts` y `src/layouts/BaseLayout.astro` anuncian `/sitemap-index.xml`. `/sitemap-events.xml` se genera durante el build desde `getPublishedEvents` y `getEventUrl`, con `updatedAt` como `lastmod`. La integración no enumera fichas SSR dinámicas por sí sola; conservar el endpoint y su registro. Verificar el índice y ambos sitemaps después del build.
- El RSS se genera en `src/pages/rss.xml.ts` con `@astrojs/rss` y se publica en `/rss.xml`. Mantén su título, descripción, idioma, fechas y enlaces coherentes con los datos del sitio y los artículos publicados.
- Reutiliza `getPublishedEvents`, `getPublishedEventCards` y `getArchivedEventGroups` de `src/lib/events/content.ts`; `getEventUrl`, `formatEventDate` y las etiquetas de estado de `src/lib/events/presentation.ts`; estados y CFP de `src/lib/events/status.ts`. Conserva el filtro de `draft` y la coherencia de las URL entre portada, catálogo, artículos, RSS, canónicas y sitemap; no dupliques estas reglas en cada consumidor.

## Mantenimiento de las instrucciones y documentación

- No edites salidas generadas en `dist/`, `.astro/` ni dependencias en `node_modules/`.
- Actualiza el `README.md` cuando cambien la configuración, el flujo de trabajo o las instrucciones para publicar contenido.
- Debes actualizar este `AGENTS.md` en la misma tarea cuando haya cambios importantes en arquitectura, tecnologías, dependencias relevantes, estructura, alias, despliegue, comandos, flujo de trabajo, RSS, sitemap o reglas del proyecto. Revisa las instrucciones existentes, corrige las que queden obsoletas y documenta las nuevas convenciones para que los siguientes agentes trabajen con información vigente.
- Mantén `AGENTS.md` y `README.md` coherentes con el código y la configuración reales; no documentes funcionalidades o validaciones que no existan o no se hayan realizado.
- Mantén los cambios dentro del alcance solicitado y conserva el trabajo existente del propietario.
